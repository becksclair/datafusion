# Flarion Database Engineer Challenge

I implemented this against Apache DataFusion `54.0.0` (`45d943dfb`) and used Apache Spark in two complementary ways:

- source checkout: `a4dc5d94` on `master`
- behavioral oracle: PySpark `4.2.0` on Java `21.0.2`

The first part of the task turned out to have two different compatibility problems hiding under one small function. The obvious one was reproducing Spark's result semantics. The less obvious one was deciding where exact Spark compatibility stops being a local Rust UDF problem and becomes an execution-architecture problem. I treated those separately rather than claiming that one native regex engine could somehow satisfy both.

## Part 1: Spark-compatible `regexp_extract`

### What I implemented

`regexp_extract` is implemented as a native DataFusion `ScalarUDFImpl`, registered in the Spark function package and callable through DataFusion's Rust/DataFrame expression API. It does not use DataFusion's SQL API.

```rust
use datafusion_expr::{col, lit};
use datafusion_spark::expr_fn::regexp_extract;

// Spark DataFrame-style three-argument form.
let selected_group = regexp_extract(
    col("subject"),
    col("pattern"),
    Some(lit(2)),
);

// Catalyst-compatible form: omitted idx defaults to group 1.
let default_group = regexp_extract(
    col("subject"),
    col("pattern"),
    None,
);
```

Relevant implementation files:

- `datafusion/spark/src/function/string/regexp_extract.rs`
- `datafusion/spark/src/function/string/mod.rs`
- `datafusion/spark/tests/regexp_extract_dataframe.rs`

### Why the public wrapper is not generated by `export_functions!`

Most Spark expression constructors in this package are exported through `export_functions!`. That macro supports fixed arity or vector arity. Spark's API is neither of those in the useful sense: it has two concrete call shapes, and the missing third argument carries a semantic default.

- `regexp_extract(str, regexp)` means group `1`
- `regexp_extract(str, regexp, idx)` evaluates the supplied `idx` expression

Representing this as a generic vector would make the Rust API less precise and move arity/default handling into call sites. I used a small typed wrapper instead:

```rust
pub fn regexp_extract(str: Expr, regexp: Expr, idx: Option<Expr>) -> Expr
```

The underlying UDF still declares both accepted signatures through `Signature::one_of`. The wrapper simply models Spark's API honestly and keeps the default in one place.

### Coercion is part of the Spark contract

A first pass that accepts only integer `idx` values is not Spark-compatible. Catalyst's `ImplicitCastInputTypes` will also coerce string indexes such as `'1'` to `IntegerType`. Spark similarly permits atomic subject and pattern expressions that can be cast to string.

The UDF therefore declares coercible signatures for both arities:

- atomic subject/pattern values are coerced to a DataFusion string type
- integer-width and string indexes are coerced to `Int32`
- the output preserves the subject representation: `Utf8`, `LargeUtf8`, or `Utf8View`

This is done in the signature layer, not by manually parsing values inside the row kernel, so DataFusion's normal planning and expression coercion remain responsible for the conversion.

### Observable semantics

The function follows Spark's first-match behavior and the result contract below:

| Case | Result |
|---|---|
| `idx = 0` | entire first match |
| `idx > 0` | corresponding capture group from the first match |
| omitted `idx` | capture group `1` |
| no regex match | empty string |
| optional group did not participate | empty string |
| subject, pattern, or index is `NULL` | `NULL` |
| negative or too-large group index after a match | execution error |
| invalid group index when there is no match | empty string |
| invalid pattern | execution error |
| pattern and index supplied as columns | evaluated per row |

Two details materially changed the implementation.

#### Empty string is not `NULL`

DataFusion's existing regex functions do not expose the same result shape. Spark's `RegExpExtractBase.extract` returns `UTF8String.EMPTY_UTF8` when there is no match and when an optional capture group did not participate. Reusing a function with different null/empty semantics would produce a superficially similar but observably wrong implementation.

Relevant Spark source:

- `sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/expressions/regexpExpressions.scala`
- `RegExpExtractBase.extract`, around lines 792-817
- `RegExpExtract`, around lines 862-900

#### Group validation happens after matching

Spark calls `matcher.find()` before validating `idx`. As a result, an invalid index behaves differently depending on whether the row matched:

- no match: return `""`, never inspect the group index
- match: validate `idx`, then return the group or raise an error

That ordering is unintuitive enough that I verified it independently against PySpark and covered it directly in the Rust tests. The kernel preserves the same order instead of validating all indexes eagerly.

### Optimization pass: from a correct row loop to a bounded batch kernel

Once the Spark semantics were correct, I reviewed the first working version as a batch kernel rather than stopping at "the tests pass." The initial shape still did avoidable work in the row path: scalar literals could be expanded to batch length, capture state was rebuilt repeatedly, and group `0` went through machinery intended for capture groups.

I tightened that path in a few focused steps:

| First working shape | Final shape | Why it matters |
|---|---|---|
| scalar pattern and index arguments could be padded to the subject length | `Hint::AcceptsSingular` keeps literal pattern and index arguments as one-element arrays | avoids materializing and repeatedly indexing values that are constant for the whole batch |
| regex compilation followed the row loop directly | a one-entry, last-pattern cache is kept for the current batch | removes repeated compilation for literals and runs of equal patterns, while still supporting row-varying patterns |
| capture bookkeeping was recreated for each matching row | one `CaptureLocations` instance is created with the compiled regex and reused with `captures_read` | avoids allocating a fresh captures object per row and returns borrowed byte ranges into the input string |
| group `0` used the general capture path | group `0` calls `Regex::find` directly | skips capture-group bookkeeping when Spark only needs the entire first match |

The cache is deliberately one entry rather than a map. A multi-pattern cache might help workloads with a small rotating pattern set, but it also introduces retention policy, memory bounds, and synchronization questions that are not justified here. The one-entry policy mirrors Spark's own last-pattern cache and gives the dominant literal/run-length win with bounded state and no shared mutable UDF state.

There is still an unavoidable cost when every row carries a different pattern: each new value must be compiled to evaluate that row correctly. The implementation does not hide that behind an unbounded cache that can grow with adversarial or high-cardinality input.

I have not attached a speedup percentage to these changes because I did not run a controlled benchmark matrix. The claim is narrower and directly visible in the implementation: regex compilation, scalar expansion, capture-state allocation, and unnecessary group-zero work were removed from the common per-row path. A proper benchmark would separate literal from high-cardinality pattern columns and compare group `0` against captured-group extraction.

### The regex-language boundary

Spark's exact regex contract is Java `Pattern`. Rust's `regex` engine is deliberately different. It provides a fast, native, linear-time path, but it does not support Java-only constructs such as look-around, backreferences, atomic groups, or possessive quantifiers. Character classes and Unicode behavior also differ in places.

I considered whether a different native regex library would close that gap. It would not. PCRE2, `fancy-regex`, or another non-Java engine may support more syntax, but none makes the implementation exactly equivalent to Spark's Java expression semantics.

Apache DataFusion Comet reaches the same boundary and makes the architectural trade-off explicit:

- its exact-compatibility path runs Spark's generated Java expression and `java.util.regex` through an Arrow-direct codegen dispatcher
- the JNI crossing happens once per Arrow batch, rather than once per row
- its native Rust regex path remains available as a faster, explicitly incompatible option

References:

- [Comet regex compatibility architecture](https://datafusion.apache.org/comet/user-guide/latest/compatibility/regex.html)
- [Comet PR #4239, JVM/codegen regex dispatcher](https://github.com/apache/datafusion-comet/pull/4239)
- [Comet PR #4146, native Rust `regexp_extract`](https://github.com/apache/datafusion-comet/pull/4146)

That is the production answer I would choose if exact Spark regex compatibility were the requirement: keep the Arrow-native execution path, but dispatch regex expressions to Spark's own generated Java implementation at batch granularity. For this challenge I bounded the work to the native Rust fast lane, documented the dialect boundary clearly, and focused on matching the DataFrame/Catalyst API and observable result semantics.

## Part 2: How Spark optimizes GroupBy

The main optimization is not one clever hash table. It is the shape of the whole pipeline:

1. Catalyst rewrites the logical aggregate into a form the physical planner can execute efficiently.
2. Spark aggregates locally before the network when that is likely to reduce data.
3. It shuffles compact aggregation buffers, not every original row.
4. It chooses a physical aggregation representation that matches the key and buffer types.
5. It falls back to external sorting when memory pressure makes hashing unsafe.
6. It reuses existing partitioning/order and adapts shuffle partition sizes when possible.

### Logical planning and DISTINCT rewrites

`SparkStrategies.Aggregation` extracts grouping and aggregate expressions, normalizes floating-point grouping keys, separates distinct from non-distinct aggregates, and delegates physical construction to `AggUtils`:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/SparkStrategies.scala`
- `Aggregation`, lines 689-729

Catalyst also removes aggregate layers that only preserve distinctness and add no semantic value:

- `sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/optimizer/RemoveRedundantAggregates.scala`, lines 26-68

Multiple distinct aggregate sets require a more expensive rewrite. `RewriteDistinctAggregates` expands each distinct set into a separate logical group identified by `gid`, aggregates those paths, then combines them in an outer aggregate:

- `sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/optimizer/RewriteDistinctAggregates.scala`, lines 28-249

This is primarily a correctness rewrite. It can multiply intermediate rows, so the trade-off is explicit: support several distinct sets in one query at the cost of additional aggregation and shuffle work.

### Partial aggregation before shuffle

For a normal non-distinct aggregate, `AggUtils.planAggregateWithoutDistinct` creates two stages:

1. `Partial` aggregation within each input partition
2. `Final` aggregation after clustering by the grouping keys

Source:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/aggregate/AggUtils.scala`, lines 125-202
- partial construction: lines 162-179
- final construction: lines 186-199

The partial stage is the central network optimization. Each mapper turns many input rows into one intermediate buffer per local key. The shuffle carries keys and compact buffers, and reducers merge those buffers. For `SUM`, that means moving one partial sum per key per partition instead of every contributing row.

Spark master also contains `spark.sql.execution.bypassPartialAggregation`. For keyed, non-distinct aggregates with extremely high group cardinality, local combining may barely reduce the row count. In that case Spark can skip the partial hash stage and avoid paying its CPU/memory cost before moving almost the same amount of data anyway:

- `AggUtils.scala`, lines 132-159
- `sql/catalyst/src/main/scala/org/apache/spark/sql/internal/SQLConf.scala`, lines 4013-4023

Global aggregation is not bypassed because its partial stage always reduces each partition to one row.

A single distinct argument set needs extra phases: partial grouping by the ordinary keys plus distinct columns, `PartialMerge` after clustering by that combined key, partial distinct aggregation by the original keys, and the final aggregate:

- `AggUtils.planAggregateWithOneDistinct`, lines 204-330

### Distribution requirements and shuffle insertion

The final aggregate declares `ClusteredDistribution(groupingKeys)` through `BaseAggregateExec.requiredChildDistribution`:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/aggregate/BaseAggregateExec.scala`, lines 96-114

`EnsureRequirements` checks the child's current partitioning. If it already satisfies that clustered distribution, Spark keeps it. Otherwise it inserts a `ShuffleExchangeExec` with the required partitioning:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/exchange/EnsureRequirements.scala`, lines 56-138, particularly 121-135

This is why compatible bucketing, upstream partitioning, or a reusable exchange can remove an otherwise expensive GroupBy shuffle.

### Choosing hash, object-hash, or sort aggregation

`AggUtils.createAggregate` chooses the physical operator from the grouping-key representation and aggregate-buffer requirements:

- `HashAggregateExec` when keys are binary-stable and the mutable buffer fits `UnsafeRow`
- `ObjectHashAggregateExec` when typed imperative aggregates require JVM object state and object-hash aggregation is enabled
- `SortAggregateExec` otherwise

Source:

- `AggUtils.scala`, lines 69-123
- `Aggregate.supportsHashAggregate` and `supportsObjectHashAggregate` in `sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/plans/logical/basicLogicalOperators.scala`, lines 1291-1315

`HashAggregateExec` is the normal fast path. It uses `UnsafeFixedWidthAggregationMap`, storing an `UnsafeRow` key and mutable buffer in task-managed memory. For supported schemas Spark can generate a specialized two-level fast hash map and fuse key projection, lookup, and buffer updates through whole-stage code generation:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/aggregate/HashAggregateExec.scala`, lines 47-75, 157-174, and 389-493
- `sql/core/src/main/scala/org/apache/spark/sql/execution/aggregate/TungstenAggregationIterator.scala`, lines 164-175

The benefit is not only expected O(1) lookup. The unsafe row representation and generated update loop reduce allocation, virtual dispatch, and JVM object pressure.

### Spill and sort fallback

Hash aggregation is bounded by task memory. `TungstenAggregationIterator.processInputs` first updates the unsafe map. When it cannot allocate another buffer, it destructs the map into an `UnsafeKVExternalSorter`, spills and merges sorted runs, then completes aggregation through the sort path:

- `TungstenAggregationIterator.scala`, lines 177-225
- `HashAggregateExec.finishAggregate`, lines 203-235

This gives Spark the expected hash fast path without making query success depend on all groups fitting in memory.

`ObjectHashAggregateExec` applies the same broad strategy to arbitrary JVM aggregation state, but it cannot account for object memory as precisely. It tracks entry count and switches remaining input to sort-based processing to avoid excessive live objects and GC pressure:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/aggregate/ObjectHashAggregateExec.scala`, lines 35-58 and 83-124
- `sql/core/src/main/scala/org/apache/spark/sql/execution/aggregate/ObjectAggregationIterator.scala`, lines 149-180

### Reusing ordering and adapting the reduce side

`SortAggregateExec` processes rows ordered by the grouping expressions, one contiguous group at a time:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/aggregate/SortAggregateExec.scala`, lines 32-58

After distribution and ordering requirements are established, `ReplaceHashWithSortAgg` can replace hashing when the child is already ordered correctly. That avoids hash computation and table maintenance without adding a new sort:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/ReplaceHashWithSortAgg.scala`, lines 26-119
- rule ordering in `sql/core/src/main/scala/org/apache/spark/sql/execution/QueryExecution.scala`, lines 748-782

With Adaptive Query Execution enabled, `CoalesceShufflePartitions` uses map-output statistics to merge small shuffle partitions and avoid launching many tiny reduce tasks:

- `sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/CoalesceShufflePartitions.scala`, lines 30-129

AQE does not change GroupBy semantics. It improves the runtime shape of the shuffle when the static partition count does not match the actual data volume.

### GroupBy summary

Spark's main GroupBy win is map-side partial aggregation followed by a key-partitioned merge. The rest of the machinery protects and extends that core idea: Catalyst rewrites difficult logical forms, the planner inserts only the distribution changes it needs, physical operators match the key/buffer representation, code generation and unsafe rows keep the hot path compact, spill converts memory pressure into external sorting, and AQE sizes the reduce side from observed data.

Compared with a naive implementation that ships every row into one global hash table, this substantially reduces network traffic and allocation while retaining a robust path for high cardinality, complex aggregate state, and constrained memory.
